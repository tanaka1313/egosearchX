# lessons

ユーザーから修正を受けたら、1ミスにつき1ルールを追記する。

形式：
- Mistake: 何が間違っていたか
- Rule: 次回どうするか
- Check: 早期に検出する方法

## コマンド1つで済む作業
- Mistake: Claude の GitHub Actions 連携の認証方式を、コマンドを打つだけで済む作業なのに細かく質問した。
- Rule: 公式コマンド1つで済む作業は、手順の詳細を計画や Issue に書かず、コマンド名だけ示す。
- Check: 質問や Issue 本文を書く前に「これはユーザーがコマンドを打つだけで済むか」を確認する。

## 警告の出し方
- Mistake: 警告の表示方法を指定しないまま仕様化したため、モーダルで出る余地が残っていた（ユーザーから「ダイアログではなく下部かタブに」と指摘）。
- Rule: 警告・通知は操作を止めない場所（下パネル、インライン、アイコン）に出す。モーダルは、元に戻せない操作の確認にだけ使う。
- Check: 仕様書や実装で、警告系の文言が `Dialog`／`alert`／`confirm` を使っていないか検索する。

## 未公認の挙動の採用と期間の表し方
- Mistake: 実機で動いた未公認の挙動（Yahoo の `OR` など）をどう扱うかの基準を持たず、採用の判断をユーザーに委ねた。また、検証の手順で期間を UNIX 秒で示した。
- Rule: 公式の記載が無い方法は、代替手段があれば使わない。代替手段が無ければ実機の挙動を優先して採用し、リスクを `docs/requirements.md` 7章に書く。期間は人が読める日付で出力し、手順にも日付で書く。
- Check: 演算子や URL パラメータを採用するとき、確度（公式／実機／二次）と代替手段の有無を表にしたか。クエリや手順に UNIX 秒が出ていないか。

## 満たせない完了条件の扱い
- Mistake: Issue #5 で、他の Issue（#8）に依存する完了条件を満たさないまま、コメントで補足するだけでクローズした。
- Rule: 対応が困難な完了条件や、他の Issue で扱うべき完了条件は、Issue 本文の完了条件を修正してからクローズする（移した先の Issue を明記する）。ユーザーに判断を仰ぐ必要はない。
- Check: クローズする前に、完了条件を1行ずつ照合し、満たしていない行が残っていないか確認する。

## ユーザーが決める表示範囲を自分で決めた
- Mistake: ランチャー画面で「いつものエゴサ」を非表示にする判断を、確認せずに自分で決めた（ユーザーは「いつものエゴサこそがランチャー」と指摘）。
- Rule: 表示・非表示の例外を作るときは、ユーザーの意図（どのページでも、など）と食い違わないかを確認する。迷う例外は作らず、全ページ共通にする。
- Check: 「どのページでも」と言われた要素に、条件分岐（例外）を入れていないか。

## 「mainにマージ」と言われたら push まで行う
- Mistake: 「ブランチを切って作業し、最後はmainにマージして。レビューは不要」と言われたのに、ローカルの main へのマージで止め、push しなかった（外部に出る操作だからと自分で止めた）。
- Rule: 「mainにマージ」「レビュー不要」と言われたら、ローカルでマージしたあと `git push origin main` まで行う。この指示は push の承認を含む。ユーザーに確認し直さない。AGENTS.md など自動生成物はコミットに入れない。
- Check: 作業の最後に `git status -sb` で main が `origin/main` より進んでいないか（ahead が残っていないか）確認する。

## あいまいな語を自分で解釈して実装した
- Mistake: 「条件のコピーボタン」を、確認せずに「ボタンの複製」と解釈して実装した（実際はクリップボードへのコピー）。
- Rule: 「コピー」「保存」「管理」のように複数の意味に取れる語は、実装前に1行で解釈を示すか、安い方の解釈を選ぶ。解釈を採ったときは、完了報告の冒頭で明記する（今回は報告で明記したため、1往復で直せた）。
- Check: 機能名を動詞だけで受けたとき、「何を何にするか」を言い換えて2通り以上に取れないか確認する。

## 「共通化」の指示の範囲を確かめずに進めた
- Mistake: 「よく使う部品だから共通コンポーネントに」という指示を、UI の置き場所（右側のシート）まで共通にすることだと受け取った。ユーザーが意図していたのは内部処理の共通化だった。
- Rule: 「共通化」と言われたら、内部の処理・状態なのか、画面の部品なのか、置き場所なのかを分けて考える。迷うときは内部だけを共通にし、置き場所は画面ごとに決める。
- Check: 共通化した結果、ある画面の UI が別の画面の都合（幅・出し方）に縛られていないか。

## サービス名を勝手に短縮した
- Mistake: 検索先「Yahoo!リアルタイム検索」を、警告・トースト・バッジ・選択肢・説明文で「Yahoo」と短縮して書いた（ユーザーの指摘：短縮はボタンだけの例外）。
- Rule: 外部サービスは正式名で書く。短縮してよいのは、ユーザーが許した場所（［Yahoo で開く］ボタン、［⋯］の項目、お気に入りの管理の行の検索先バッジ）だけ。表示名は定数1か所（`ENGINE_LABEL`）から出し、文言に直書きしない。
- Check: `grep -rn "Yahoo" src` で、正式名・ボタン・識別子・URL 以外の「Yahoo」が残っていないか。

## 保存する値を、画面に見えない設定から取っていた
- Mistake: お気に入りの検索先を、☆ 保存の画面では選ばせず、詳細条件の奥にある「エンジン」の設定から黙って取っていた。履歴・URL解析からの保存は X 固定、実行時は検索先を無視していた（ユーザーの指摘：「X なのか Yahoo なのかを覚えておく場所が無い」）。
- Rule: 保存データの項目は、保存する画面で見えて選べるようにする。同じデータを作る・直す画面がいくつあっても、全部で同じ部品を使って選ばせる。保存した項目は、使う側（実行）で必ず参照する。
- Check: データ型の項目を1つずつ挙げて、「どの画面で入力するか」「どこで使うか」を対応表にする。入力元が別画面の設定や固定値になっていないか、使う側が無視していないか。

## 指摘を受けて足した印を、確かめずに増やした
- Mistake: 警告を枠の下に移すとき、頼まれていない「!」の印を［Yahoo で開く］に足し、不要と言われた。
- Rule: 指摘への対応は、言われたことだけを行う。補助の印・バッジなど、頼まれていない UI 要素は足さない（足したいなら計画で1行聞く）。
- Check: 計画の各項目が、ユーザーの言葉のどれに対応するか言えるか。対応しない項目が無いか。
