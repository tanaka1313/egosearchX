# lessons

ユーザーから修正を受けたら、1ミスにつき1ルールを追記する。

形式：
- Mistake: 何が間違っていたか
- Rule: 次回どうするか
- Check: 早期に検出する方法

## コマンド1つで済む作業
- Mistake: Claude の GitHub Actions 連携の認証方式を、コマンドを打つだけで済む作業なのに細かく質問した。
- Rule: 公式コマンド1つで済む作業は、手順の詳細を計画や Issue に書かず、コマンド名だけ示す。
- Check: 質問や Issue 本文を書く前に「これはユーザーがコマンドを打つだけで済むか」を確認する。

## 警告の出し方
- Mistake: 警告の表示方法を指定しないまま仕様化したため、モーダルで出る余地が残っていた（ユーザーから「ダイアログではなく下部かタブに」と指摘）。
- Rule: 警告・通知は操作を止めない場所（下パネル、インライン、アイコン）に出す。モーダルは、元に戻せない操作の確認にだけ使う。
- Check: 仕様書や実装で、警告系の文言が `Dialog`／`alert`／`confirm` を使っていないか検索する。

## 未公認の挙動の採用と期間の表し方
- Mistake: 実機で動いた未公認の挙動（Yahoo の `OR` など）をどう扱うかの基準を持たず、採用の判断をユーザーに委ねた。また、検証の手順で期間を UNIX 秒で示した。
- Rule: 公式の記載が無い方法は、代替手段があれば使わない。代替手段が無ければ実機の挙動を優先して採用し、リスクを `docs/requirements.md` 7章に書く。期間は人が読める日付で出力し、手順にも日付で書く。
- Check: 演算子や URL パラメータを採用するとき、確度（公式／実機／二次）と代替手段の有無を表にしたか。クエリや手順に UNIX 秒が出ていないか。

## 満たせない完了条件の扱い
- Mistake: Issue #5 で、他の Issue（#8）に依存する完了条件を満たさないまま、コメントで補足するだけでクローズした。
- Rule: 対応が困難な完了条件や、他の Issue で扱うべき完了条件は、Issue 本文の完了条件を修正してからクローズする（移した先の Issue を明記する）。ユーザーに判断を仰ぐ必要はない。
- Check: クローズする前に、完了条件を1行ずつ照合し、満たしていない行が残っていないか確認する。

## ユーザーが決める表示範囲を自分で決めた
- Mistake: ランチャー画面で「いつものエゴサ」を非表示にする判断を、確認せずに自分で決めた（ユーザーは「いつものエゴサこそがランチャー」と指摘）。
- Rule: 表示・非表示の例外を作るときは、ユーザーの意図（どのページでも、など）と食い違わないかを確認する。迷う例外は作らず、全ページ共通にする。
- Check: 「どのページでも」と言われた要素に、条件分岐（例外）を入れていないか。

## 「mainにマージ」と言われたら push まで行う
- Mistake: 「ブランチを切って作業し、最後はmainにマージして。レビューは不要」と言われたのに、ローカルの main へのマージで止め、push しなかった（外部に出る操作だからと自分で止めた）。
- Rule: 「mainにマージ」「レビュー不要」と言われたら、ローカルでマージしたあと `git push origin main` まで行う。この指示は push の承認を含む。ユーザーに確認し直さない。AGENTS.md など自動生成物はコミットに入れない。
- Check: 作業の最後に `git status -sb` で main が `origin/main` より進んでいないか（ahead が残っていないか）確認する。

## あいまいな語を自分で解釈して実装した
- Mistake: 「条件のコピーボタン」を、確認せずに「ボタンの複製」と解釈して実装した（実際はクリップボードへのコピー）。
- Rule: 「コピー」「保存」「管理」のように複数の意味に取れる語は、実装前に1行で解釈を示すか、安い方の解釈を選ぶ。解釈を採ったときは、完了報告の冒頭で明記する（今回は報告で明記したため、1往復で直せた）。
- Check: 機能名を動詞だけで受けたとき、「何を何にするか」を言い換えて2通り以上に取れないか確認する。

## 「共通化」の指示の範囲を確かめずに進めた
- Mistake: 「よく使う部品だから共通コンポーネントに」という指示を、UI の置き場所（右側のシート）まで共通にすることだと受け取った。ユーザーが意図していたのは内部処理の共通化だった。
- Rule: 「共通化」と言われたら、内部の処理・状態なのか、画面の部品なのか、置き場所なのかを分けて考える。迷うときは内部だけを共通にし、置き場所は画面ごとに決める。
- Check: 共通化した結果、ある画面の UI が別の画面の都合（幅・出し方）に縛られていないか。

## サービス名を勝手に短縮した
- Mistake: 検索先「Yahoo!リアルタイム検索」を、警告・トースト・バッジ・選択肢・説明文で「Yahoo」と短縮して書いた（ユーザーの指摘：短縮はボタンだけの例外）。
- Rule: 外部サービスは正式名で書く。短縮してよいのは、ユーザーが許した場所（［Yahoo で開く］ボタン、［⋯］の項目、お気に入りの管理の行の検索先バッジ）だけ。表示名は定数1か所（`ENGINE_LABEL`）から出し、文言に直書きしない。
- Check: `grep -rn "Yahoo" src` で、正式名・ボタン・識別子・URL 以外の「Yahoo」が残っていないか。

## 保存する値を、画面に見えない設定から取っていた
- Mistake: お気に入りの検索先を、☆ 保存の画面では選ばせず、詳細条件の奥にある「エンジン」の設定から黙って取っていた。履歴・URL解析からの保存は X 固定、実行時は検索先を無視していた（ユーザーの指摘：「X なのか Yahoo なのかを覚えておく場所が無い」）。
- Rule: 保存データの項目は、保存する画面で見えて選べるようにする。同じデータを作る・直す画面がいくつあっても、全部で同じ部品を使って選ばせる。保存した項目は、使う側（実行）で必ず参照する。
- Check: データ型の項目を1つずつ挙げて、「どの画面で入力するか」「どこで使うか」を対応表にする。入力元が別画面の設定や固定値になっていないか、使う側が無視していないか。

## 指摘を受けて足した印を、確かめずに増やした
- Mistake: 警告を枠の下に移すとき、頼まれていない「!」の印を［Yahoo で開く］に足し、不要と言われた。
- Rule: 指摘への対応は、言われたことだけを行う。補助の印・バッジなど、頼まれていない UI 要素は足さない（足したいなら計画で1行聞く）。
- Check: 計画の各項目が、ユーザーの言葉のどれに対応するか言えるか。対応しない項目が無いか。

## 記号の衝突を注記で避け、CLAUDE.md に重複を書いた
- Mistake: ダイアログ（M1〜M3）とマイルストーン（M0〜M7）の記号がぶつかったのに、CLAUDE.md と実装計画に「意味が違う」と注記して済ませた。また CLAUDE.md に、Makefile・ユーザースコープの CLAUDE.md・`testing.md`・docs と同じ内容を書き写していた。
- Rule: 記号や用語がぶつかったら、注記で避けずに片方を改名する（ダイアログは D1〜D3）。CLAUDE.md には、どの変更にも効く不変条件と、ほかで読み込まれない規則だけを書く。画面の細部は docs に任せ、参照先を示す。
- Check: 「〜は文書によって意味が違う」という注記を書こうとしていないか。CLAUDE.md に足す行が、Makefile・`.claude/rules`・ユーザースコープ・docs にすでに無いか grep する。

## 仕様書をモックと照合せず、上書きを重ねた
- Mistake: モックを直すたびに画面仕様書へ部分的に追記したため、モックに無い要素（パンくず、お気に入りの最終実行、ランチャーの確認）や、同じ事実の重複（警告の置き場所が4か所）が長く残った。
- Rule: モックを変えたら、仕様書の該当する節を、モックのファイルを開いて照合する。部品の振る舞いは共通部品の章に1回だけ書き、画面の節からは名前で参照する。仕様にあってモックに無い要素は、黙って残さずユーザーに確認する。
- Check: 仕様書の各節に、対応するモックのファイルを言えるか。同じ文言（例：「警告」「モーダル」）を grep して、2か所以上に説明が無いか。

## ユーザーが記録済みの結果を、読まずにユーザー作業へ入れた
- Mistake: 実機確認の結果が Issue（#49）のコメントに残っていたのに、読まずに「ユーザーの作業」として計画に入れ、確認を頼み直した。
- Rule: 「ユーザーの作業」に入れる前に、対応する Issue のコメントと文書を読み、済んでいないかを確かめる。結果が文書の前提と食い違えば（今回は `until:` が指定日を含んだ）、仕様の見直しとして報告する。
- Check: ユーザー作業の表の各行について、`gh issue view <番号> --comments` で結果が無いことを確認したか。

## 依頼の意味が伝わらない書き方をした
- Mistake: 「英語名でもそのまま使うか」と書き、画面のどこの何の話か伝わらず、ユーザーに聞き返された。
- Rule: 決めてもらうことは、画面のどこに何が出るかの具体例（例：英語の画面のヘッダー［ホロライブ▾］を［hololive▾］にするか）と選択肢で書く。内部の用語（固有名詞、辞書など）だけで書かない。
- Check: 質問文だけを読んで、画面を見たことのない人が答えられるか。

## 「API」を、サーバーの API と決めつけて選択肢を作った
- Mistake: サーバーを持たないアプリで「API仕様書」と言われ、将来の REST API か、モジュールの関数かを選ばせる選択肢を作ったが、実際の意図は「フロントとバックを分けて実装するための境界」だった（ユーザーの指摘：「将来性のことではないです」）。
- Rule: 技術用語（API・バックエンド・サービス）が、アプリの構成（静的書き出し・サーバー無し）と合わないときは、選択肢を作る前に「この構成では何を指すか」を自由記述で聞くか、意図を言い換えて1行で確認する。
- Check: 質問の選択肢が、すべて自分の想像から作られていないか。ユーザーの言葉（「便宜上分けて」など）を選択肢に入れたか。

## 「画面にあるはず」と言われた項目を調べずに聞き、外部仕様の事実を先に伝えなかった
- Mistake: ユーザーが「lastRunAt は画面に表示しているはず」と言った項目は、仕様書にもモックにも無かった。また、X の最新タブ（`f=live`）を検索文字列の記号にする案を、「`f=` は URL のパラメータで、検索欄に入れる演算子ではない」という事実を先に伝えずに出し、質問を何度も聞き直させた。
- Rule: ユーザーが「あるはず」と言ったものは、まず grep で仕様書・モック・スキーマを調べ、無ければ「無かった」と事実を先に伝えてから聞く。外部サービスの仕様が絡む案は、案を出す前に事実（どこで指定する値か）を1行で添える。
- Check: 質問文に、調べた結果（ある／無い）と根拠のファイルが入っているか。

## 値付きのボタンのラベルに値を書き、相対期間をボタンにした
- Mistake: プリセットの Excel に、ラベルへ値を含めた「ファボ 50件以上」「RT 10件以上」を入れ、`since:yesterday` を条件ボタンにした。画面は「ラベル［値］件以上」と出すので二重になり、`since:` の後ろは日付として読まれるので `yesterday` は入力欄で不正な値になる（ユーザーの指摘：「10は可変にできるはずだよね？」）。
- Rule: データ（プリセット・Excel）を書く前に、その値を表示・解析する部品（`PARAM_OPS`、`ParamChip`、`tokenToCond`）を読む。値付きの条件（min_faves／min_retweets／min_replies の数値、since／until の日付）は、Excel では画面と同じ形（`ファボ [50]件以上`、`日付 [2026-11-07] 以降`、`日付 [2026-11-14] 以前`）でラベルを書き、JSON のラベルは `[` より前だけにする（ユーザーの指示）。相対期間はボタンにせず、ホームの「期間」で選ぶ。
- Check: プリセットの行ごとに、「画面にどう出るか」を1行で言い換えられるか。値付きの行のラベルが `名前 [値]単位` の形で、`[ ]` の値が検索文字列と一致しているか。

## 目的を説明できない列（キー）をひな形に作った
- Mistake: プリセットの Excel に「キー」列を作ったが、使い道は条件ボタンの ID（`<対象>:<key>`）だけで、検索文字列の一致で足りた。ユーザーに「キーの入力の必要性が分からない」と聞かれた。
- Rule: ひな形に列・項目を足す前に、「何に使い、ほかの列から導けないか」を1行で言えるか確かめる。言えなければ足さない。
- Check: 各列について、その列を読む処理（画面・JSON・照合）を挙げられるか。

## 根拠の無い暫定の数値を、別の定数にして仕様に残した
- Mistake: ブックマーク URL 全体の警告水準（2000文字）を、根拠を確かめずに別の定数にして仕様・型・画面に広げた。効く制限は X のクエリ（約500文字）で、各クエリで判定すれば足りた（ユーザーの指摘）。実装時に、`encode` がオリジンを知らないという食い違いとして表に出た。
- Rule: 上限・警告水準を足す前に、「何の制限に由来するか」を1行で言う。言えなければ作らない。制限の単位（クエリ1件か、URL 全体か）は、制限を課す側（X）の単位に合わせる。
- Check: 新しい定数・警告コードごとに、根拠（どのサービスのどの制限か）を言えるか。既存の定数（`LIMITS.urlWarn`）で足りないか。

## 質問に、説明していない内部の用語を使った
- Mistake: 質問の選択肢で「契約」（`src/api` の型・api-spec のこと）を説明なしに使い、ユーザーに「契約って何？」と聞き返された。
- Rule: 質問には、ユーザーが使っていない内部の用語（契約・マスタ・codec など）を使わず、ファイル名か「画面と裏側の境界の型」のように言い換える。
- Check: 質問文を、このリポジトリを開いていない人が読んで意味が通るか。
